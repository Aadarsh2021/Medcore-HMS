01  Executive Overview
Project Overview
MedCore HMS is a full-stack, cloud-native Hospital Management Platform designed to digitise end-to-end clinical and administrative workflows across multiple hospital branches. The platform addresses a genuine operational gap: most mid-sized hospitals in India and South-East Asia still rely on fragmented desktop software, paper registers, and WhatsApp groups to coordinate patient care.
This project challenges you to design, architect, and build a production-grade SaaS product — the kind that could realistically be licensed to hospital chains, diagnostic centres, and tele-health providers.
💡  Hint:  
Before writing any code, spend time reading how Epic Systems and Practo structure their patient encounter workflows. Understanding the domain first will help you model the database correctly.
Background & Problem Statement
A large teaching hospital processes roughly 600–900 outpatient encounters per day. Today, the admission desk uses one legacy software for patient registration, the pharmacy uses a separate billing tool, and lab technicians print results and physically deliver them to wards. A doctor finishing rounds cannot check a patient's latest haemoglobin count without walking to the lab or waiting for a phone call.
The outcome is delayed clinical decisions, duplicate diagnostic tests, billing errors, and poor patient experience. MedCore HMS eliminates these friction points through a unified, role-aware, real-time platform.
💡  Hint:  
Map out the existing paper-based or legacy workflow for at least one hospital department before designing your data models. Real requirements always hide inside processes, not in feature lists.
Product Vision
Build a scalable, HIPAA-aware Hospital Management System that serves hospitals ranging from 30-bed clinics to 800-bed multi-speciality centres — all from a single multi-tenant SaaS deployment.

03  System Architecture
Architecture Overview
MedCore HMS follows a clean, layered architecture that separates concerns between presentation, business logic, and data access. The backend exposes a RESTful API consumed by the Next.js frontend and, eventually, mobile clients.
High-Level Component Diagram (Text Representation)
[ Browser / PWA ]  ←→  [ Next.js 15 Frontend ]
                              ↕  HTTPS / REST + WebSocket
[ Nginx Reverse Proxy ]  ←→  [ NestJS API (port 3001) ]
                              ↕  Prisma ORM
[ PostgreSQL ]   [ Redis Cache ]   [ AWS S3 / Cloudinary ]
[ Socket.IO Server ]  ←→  Real-time event bus
💡  Hint:  
Draw this diagram properly in Excalidraw or draw.io and include it in your project README. Reviewers and examiners always appreciate a well-drawn architecture diagram over a text representation.
Multi-Tenancy Strategy
Each hospital operates as a tenant. All database tables that hold hospital-specific data carry a hospitalId foreign key. Middleware validates this on every request so that no tenant can ever access another tenant's data — even if they guess a record ID.
Super Admins operate across tenants; all other roles are scoped to a single hospital at authentication time.
💡  Hint:  
Research the difference between database-per-tenant, schema-per-tenant, and row-level multi-tenancy. Justify in your report which approach you chose and why it suits this project's scale requirements.
Caching Strategy
Redis is used for three purposes: (1) session storage for refresh tokens and device tracking, (2) short-lived caches for expensive read queries (doctor availability slots, medicine inventory counts), and (3) rate-limiting counters to protect public endpoints.
💡  Hint:  
A common mistake is over-caching. Cache only data that is read far more often than it is written. Doctor availability changes frequently — cache it with a TTL of 60 seconds, not 1 hour.

Key Design Decisions You Must Make
How will you store doctor availability? A repeating weekly schedule vs. individual time slots — each has trade-offs.
How will you handle the many-to-many relationship between a prescription and medicines (dosage, frequency, duration differ per item)?
How will lab test results be stored? Structured key-value pairs vs. a file attachment vs. a hybrid approach?
What indexes will you create? At minimum: hospitalId, patientId, doctorId, appointmentDate, and any column used in WHERE clauses.
💡  Hint:  
Run EXPLAIN ANALYZE on your slowest queries during development. Add indexes based on what the query planner tells you, not on what you assume will be slow.

07  Module Specifications
Module Breakdown
7.1  Authentication Module
Authentication is the foundation of the platform. Every other module depends on knowing who the caller is and what they are allowed to do.
Required Endpoints
POST /auth/register — create account with email verification
POST /auth/login — issue access token (15 min TTL) + refresh token (7 days, stored in httpOnly cookie)
POST /auth/refresh — exchange refresh token for new access token
POST /auth/forgot-password — send reset link via email
POST /auth/reset-password — validate token, update hashed password
POST /auth/verify-email — confirm email via 6-digit OTP
POST /auth/verify-phone — confirm phone via SMS OTP (Twilio)
POST /auth/logout — revoke refresh token in Redis
GET  /auth/me — return current user profile with permissions
💡  Hint:  
Store refresh tokens in Redis with the key pattern rt:{userId}:{deviceId}. This lets you invalidate a single device session or all sessions at once — useful for 'Log out of all devices'.
💡  Hint:  
Hash passwords with bcrypt at cost factor 12. Never log passwords, tokens, or OTPs — add a log sanitiser that strips these fields from all console output.
7.2  Appointment Module
The appointment module is the central scheduling engine. It must handle concurrent booking attempts gracefully and ensure no doctor is double-booked.
Business Rules
A doctor works in one or more departments and defines time slots (e.g., 9:00–13:00, 30-minute intervals).
A patient cannot have two appointments at the same time across any doctor.
Appointments can be in states: PENDING → CONFIRMED → IN_PROGRESS → COMPLETED | CANCELLED | NO_SHOW
Emergency bookings bypass the normal slot availability and flag the appointment as EMERGENCY.
Appointment reminders are sent 24 hours and 1 hour before via email + SMS (BullMQ scheduled jobs).
Concurrency Challenge
When two patients try to book the same slot simultaneously, only one should succeed. You must implement either database-level locking (SELECT FOR UPDATE) or an optimistic concurrency pattern.
💡  Hint:  
Research 'database row locking in PostgreSQL' and 'optimistic vs pessimistic concurrency control'. Implement whichever pattern you choose and document your reasoning in the report.
7.3  Electronic Medical Records (EMR)
A Medical Record is created when a doctor starts an appointment encounter. It is append-only — doctors can add notes but cannot delete past entries.
EMR Data Points
Vitals: BP, pulse, temperature, SpO2, height, weight, BMI (auto-calculated)
Chief complaint and presenting symptoms
Differential and confirmed diagnosis (mapped to ICD-10 codes where possible)
Treatment plan with instructions
Allergies and adverse drug reactions
Vaccination history (date, vaccine name, batch number, next due date)
Family history flags (diabetes, hypertension, cancer, cardiac)
Attached files: scanned documents, images (stored in S3, max 20 MB per file)
💡  Hint:  
HIPAA requires that medical records be encrypted at rest and in transit. For this project, enable PostgreSQL column-level encryption for diagnosis and notes fields, or document why row-level security is sufficient.
7.4  Prescription Module
Doctors issue prescriptions at the end of an encounter. The prescription is linked to a medical record and can be printed or downloaded as a signed PDF.
Prescription Fields
Medicine name (searchable from the pharmacy inventory)
Form: tablet / capsule / syrup / injection / topical
Dosage (e.g., 500 mg), frequency (OD / BD / TDS / QID / SOS), duration (days)
Special instructions (take after food, avoid sunlight, etc.)
Digital signature of the doctor (stored as SVG or PNG, overlaid on PDF)
💡  Hint:  
Generate prescription PDFs using Puppeteer (headless Chrome) rather than a PDF library — you can design a proper HTML template and convert it. The output looks far more professional and can include the hospital letterhead.
7.5  Laboratory Module
Lab technicians receive orders generated by doctors during an encounter. Results are uploaded and go through a review workflow before the patient can see them.
Lab Workflow
Doctor creates a LabOrder (linked to MedicalRecord) with one or more tests
Receptionist or Lab Tech receives the order — status changes to SAMPLE_COLLECTED
Lab Tech processes the sample and uploads a structured result or PDF report
Senior Lab Tech or Lab Manager reviews and approves the report
Patient and Doctor are notified — report is now visible in both portals
💡  Hint:  
Model lab test reference ranges (e.g., Haemoglobin: 13.0–17.5 g/dL for males) in the database so the system can automatically flag out-of-range values in red on the report.
7.6  Pharmacy Module
The pharmacy manages medicine stock and fulfils prescriptions. Expiry tracking and low-stock alerts are critical patient-safety features.
Inventory Rules
Each medicine batch has: batch number, manufacturing date, expiry date, quantity, unit cost, MRP.
FIFO (First In, First Out) dispensing — oldest batch is consumed first.
Low-stock alert: when quantity falls below the reorder level (configurable per medicine).
Expired stock is flagged and must be quarantined — it cannot be dispensed.
💡  Hint:  
Implement a nightly BullMQ job that scans for medicines expiring within 30 days and sends a report to the Pharmacist and Hospital Admin. This simulates a real production job that prevents patient-safety incidents.
7.7  Billing & Payments
The billing module aggregates charges from all departments (consultation fee, lab tests, medicines, room charges) into a single invoice per visit.
Invoice Lifecycle
Items are added to a draft invoice as services are rendered during the visit
Receptionist or Accountant finalises the invoice and shares it with the patient
Patient pays via one of: Stripe card, Razorpay UPI/Netbanking, or cash at counter
Payment confirmation triggers a receipt email and updates the invoice status to PAID
Insurance claims follow a separate TPA (Third Party Administrator) workflow
💡  Hint:  
Never trust payment confirmation from the client side. Always verify payment status by calling the Stripe or Razorpay webhook handler and comparing signatures. The test suite should include a simulated payment webhook test.
7.8  Notification System
All notifications are generated as events inside the backend. A notification worker subscribes to the event bus and dispatches via the appropriate channel.
Trigger Event

💡  Hint:  
Use a fan-out pattern: one event → multiple notification handlers (EmailHandler, SMSHandler, PushHandler). Each handler runs in its own BullMQ queue so a failed SMS does not block the email from sending.
08  API Contract
REST API Design Guidelines
All APIs follow RESTful conventions with consistent response envelopes and error shapes.
Standard Response Envelope
Success:
{ "success": true, "data": { ... }, "message": "OK" }
Error:
{ "success": false, "error": { "code": "SLOT_UNAVAILABLE", "message": "This slot was just booked by another patient." } }
Paginated List:
{ "success": true, "data": [...], "meta": { "page": 1, "limit": 20, "total": 348, "totalPages": 18 } }

10  Security Requirements
Security Implementation Checklist
Medical data is among the most sensitive categories of personal information. These requirements are non-negotiable.
Security Control
Implementation Requirement
Password Hashing
bcrypt with minimum cost factor 12
Transport Security
HTTPS enforced everywhere; HTTP redirects to HTTPS at Nginx
JWT Secrets
Minimum 256-bit random secret; stored in environment variable only
Refresh Token Rotation
Issue new refresh token on every use; invalidate the old one
Rate Limiting
100 req/15 min per IP on auth endpoints; 1000 req/min on API
CORS
Strict allow-list — only your frontend domain(s)
Helmet.js
All recommended HTTP security headers enabled
SQL Injection
Prisma parameterised queries prevent injection by default — never use raw()
XSS
Sanitise all user-supplied HTML input using DOMPurify (frontend)
CSRF
SameSite=Strict on cookies; CSRF token on state-changing requests
Input Validation
Zod on frontend; class-validator + class-transformer on NestJS DTOs
Audit Logging
Every create/update/delete operation logged with userId, IP, timestamp
File Upload
Validate MIME type + file extension; scan with ClamAV or reject executables
Data Encryption
Sensitive columns (diagnosis, notes) encrypted at rest using pgcrypto
💡  Hint:  
Set up Sentry from day one, not at the end. It will catch unhandled promise rejections in your background jobs that would otherwise be silent failures in production.

On release tag: deploy to production (blue-green deployment with health check gate)
💡  Hint:

A Note from the Project Coordinator
This project is intentionally ambitious for a solo 4-week build. You are not expected to ship every module to perfection. You are expected to make considered engineering decisions, justify them in your report, and produce working software that demonstrates your understanding of the full stack.
Prioritise depth over breadth. A fully working Auth + Appointments + EMR + Billing flow — with proper validation, error handling, and tests — is far more impressive than ten half-built modules. Build the core journey end-to-end first, then layer on additional features if time allows.
Four weeks will go faster than you think. Commit code every single day. Deploy early — even a broken deployment on Day 3 is better than a deployment crisis on the final day. The ability to ship consistently under time pressure is exactly what this project is designed to test.
